# Deploying SkillSwap

One Render web service serves everything: Express handles `/api` and
`/socket.io`, and serves the built React client for every other path. The
database is MongoDB Atlas.

```
                    ┌──────────────────────────────┐
  Browser ─────────▶│  Render web service          │
    one origin      │    /api/*       Express      │
                    │    /socket.io/* Socket.io    │
                    │    /*           React build  │
                    └──────────────┬───────────────┘
                                   │ mongodb+srv
                    ┌──────────────▼───────────────┐
                    │  MongoDB Atlas (free M0)     │
                    └──────────────────────────────┘
```

## Why one service

**Socket.io needs a long-lived process.** That rules out serverless platforms
— Vercel in particular cannot host a WebSocket server, so the real-time chat
simply would not run there.

Serving the client from the same process buys three things beyond that:

- **No CORS.** The browser only ever talks to one origin.
- **Socket.io needs no configuration.** It connects back to the host that
  served the page.
- **No cold-start gap.** Render's free tier sleeps after 15 minutes idle, but
  loading the page is what wakes it — by the time JavaScript calls the API,
  the service is already up. Split across two hosts, the first API call would
  have to absorb that wait.

It also matches the local Docker setup, where Nginx proxies `/api` to the
server. Development and production have the same shape.

## 1. MongoDB Atlas

**you** — create a free **M0** cluster at [mongodb.com/atlas](https://www.mongodb.com/atlas).

1. **Database Access** → add a user, and note the password.
2. **Network Access** → add `0.0.0.0/0`. Render's free tier has no static
   outbound IP, so the cluster has to accept any address. The database is
   still protected by its credentials.
3. **Connect** → *Drivers* → copy the `mongodb+srv://…` string and put your
   password into it. Add the database name before the query string:

   ```
   mongodb+srv://user:pass@cluster.xxxxx.mongodb.net/skillswap?retryWrites=true&w=majority
   ```

## 2. Render

**you** — at [render.com](https://render.com): **New → Blueprint**, pick the
`skillswap` repository. Render reads [`render.yaml`](render.yaml), creates the
service, and asks for the one secret it cannot generate:

| Variable | Value |
|----------|-------|
| `MONGO_URI` | the Atlas string from step 1 |

`JWT_SECRET` is generated automatically, and `CLIENT_ORIGIN` resolves to the
service's own URL. Everything else has a default in the blueprint.

First deploy takes a few minutes: it installs both halves, builds the client,
then drops the client's build-time dependencies.

## 3. Seed the demo data

Optional, and only useful for a demo. **Render dashboard → your service →
Shell**:

```bash
node server/src/seed/seed.js
```

Seven members around Hyderabad with overlapping skills, a history of
completed swaps, reviews and challenges. Every account uses `password123` —
fine for a demo, so change or drop them before anything real.

## 4. Check it

```bash
curl https://<your-service>.onrender.com/api/health
```

`{"success":true,...,"database":"connected"}` means both halves are up. Then
open the URL, log in, and confirm the Messages page shows **live** — that dot
is the Socket.io connection, and it is the thing a serverless host could not
give you.

## Environment variables

Set by the blueprint unless marked otherwise.

| Variable | Notes |
|----------|-------|
| `MONGO_URI` | **You set this.** The Atlas connection string |
| `JWT_SECRET` | Generated by Render |
| `CLIENT_ORIGIN` | The service's own URL |
| `PORT` | Render provides it; the server reads it |
| `DNS_SERVERS` | `8.8.8.8,1.1.1.1` — Atlas resolves through SRV records, and some networks drop them |
| `JWT_EXPIRES_IN` | `7d` |
| `CREDITS_PER_HOUR` | `1` |
| `SIGNUP_BONUS_CREDITS` | `3` |

## Continuous deployment

Render redeploys on every push to `main` by default. Jenkins already builds
and pushes images on each change, so the two run side by side: Jenkins is the
quality gate, Render is the host.

To gate deploys on a green pipeline instead, turn off auto-deploy in Render
and use its deploy hook from the Jenkinsfile's `Deploy` stage — the Coolify
branch is already shaped for exactly that, and only the URL changes.

## Free tier limits

| | |
|---|---|
| Sleeps after | 15 minutes idle |
| Cold start | ~50 seconds, absorbed by the page load |
| Atlas M0 storage | 512 MB |

A paid Render instance removes the sleep. Nothing in the code depends on it.

## Troubleshooting

| Symptom | Cause |
|---------|-------|
| `/api/health` says `database: disconnected` | `MONGO_URI` wrong, or Atlas Network Access does not include `0.0.0.0/0` |
| Site loads, API calls 404 | The client build is missing — check the build log for `npm run build`, and the start log for `Serving the client build from …` |
| Messages shows **offline** | Socket.io could not connect. On Render this should not happen; if it does, confirm the service is a web service, not a static site |
| `querySrv ETIMEOUT` at startup | DNS cannot resolve the Atlas SRV record. `DNS_SERVERS` exists for this |
| Deep links 404 on refresh | The SPA fallback is not running — it is skipped when no client build is found |
